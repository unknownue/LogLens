# 文件编码（encoding）

窗口底部状态栏右侧显示当前文件按什么编码解码，点它打开编码弹窗切换：

```
┌────────────────────────────────────────────────────────────┐
│  … 正文 …                                                   │
├────────────────────────────────────────────────────────────┤
│ 12,345 行                          UTF-8 · 自动(合法 UTF-8) │  ← 状态栏
└────────────────────────────────────────────────────────────┘
```

弹窗是「左列表 + 右预览」：选一个编码，右边立刻显示**文件头部按那个编码解出来长什么样**
（前 14 行）。选好后点「应用并重新加载」才真正重载 —— 换编码要重建后端会话并整体替换视图
（滚动位置回到文件尾部），值得一次显式确认。

本文说明这套功能怎么实现、边界在哪、以及踩过的坑。

## 为什么需要它

在此之前整条读取链路都写着 `String::from_utf8_lossy`，即**假定 UTF-8**。中文 Windows 上
这会导致两类真实故障：

| 文件实际编码 | 旧行为 | 现在的行为 |
|--------------|--------|-----------|
| UTF-8 | 正常 | 正常 |
| GBK / GB18030（ANSI 936） | 中文全变 `����` | 自动识别并正确显示 |
| UTF-16LE（PowerShell `Out-File`、`>` 重定向的默认输出） | 每行被拆成两半 + 全是乱码 | 按 2 字节换行正确切行 |
| Big5 / Shift_JIS / Latin-x | 乱码 | 可在弹窗里手动选 |

## 三个关键设计

### 1. 解码收敛到一处：`src-tauri/src/encoding.rs`

「字节 → 文本」这一步全部走 `encoding::decode_line` / `decode_all`，底层是
[`encoding_rs`](https://crates.io/crates/encoding_rs)（Firefox 用的那份 WHATWG Encoding
标准实现，纯 Rust 无 C 依赖，自带 BOM 嗅探与按编码 lossy 解码 —— 非法字节替换为 U+FFFD，
与既有 `from_utf8_lossy` 同语义、不 panic）。

`tools/verify-encoding.test.mjs` 里有一条守卫断言：**读取链路（tail / search / document /
state / index）的正文里不许再出现 `from_utf8_lossy`**。它是「一律按 UTF-8 解」时代的标志，
回归一次就是 GBK 日志全变乱码。

### 2. 行切分仍在字节层做，但换行符形态随编码变化

ASCII 兼容的编码（UTF-8 / GBK / Big5 / Shift_JIS / EUC / Latin-x）里，多字节字符的尾字节
取值区间**都不含 `0x0A`**，所以 `0x0A` 只可能是真正的换行 —— 这一族不需要任何额外处理，
既有的「按字节偏移 + 稀疏虚拟滚动」设计完全不受影响。

UTF-16 是唯一的例外：换行是 2 字节（LE 是 `0A 00`，BE 是 `00 0A`）。于是 `LineTerm`
承担三件事：

```rust
enum LineTerm { Lf, Lf16Le, Lf16Be }
```

- **切行**（`encoding::split_complete`）：按对应的字节序列切，并剥掉行尾同样宽度的 `\r`；
- **行号索引**（`index.rs`）：统计换行数、记录采样偏移时必须数**同一种**换行 —— 按裸
  `0x0A` 去数 UTF-16 会在偏移上错位一格，定位出来的行首全是半个字符；
- **对齐**：UTF-16 的换行只在与行首同奇偶的偏移上匹配。否则 `U+0A05 U+0B00`
  （UTF-16LE 下字节是 `05 0A 00 0B`）在偏移 1 处会与 `0A 00` 撞出一个**假换行**。
  真实日志里这种组合近乎不可能出现，但「近乎」不是「不会」，而对齐判定只多一次取模。

由此还带出两条不变量，都由 `LineTerm::align_chunk` + 索引的两处扫描循环守住：

1. **块读取长度必须是换行符宽度的整数倍**。奇数块会让后续每个块的起点奇偶整体翻转，
   一个恰好横跨块边界的换行符就会两边都不认 —— 前一块凑不满 2 字节、后一块的绝对
   偏移是奇数。实测后果：200 行被数成 133 行，之后每个采样偏移都错一行。
2. **扫不动那点尾巴时停下，不要吃进 `covered_bytes`**。不足一个换行符宽度的尾巴
   只可能出现在文件末尾，而它不可能是完整换行符（换行符只从对齐偏移开始），
   所以停下等价于「读到 EOF，且末行没有换行结尾」。

第 2 条是给**写了一半的日志**准备的，而这个应用正是天天在读别人正在写的文件：
一个 UTF-16 日志当前大小是奇数时（换行符只刷进来一半），若此刻把 `covered_bytes`
推到那个奇数偏移上，等文件增长后，横跨边界的那个换行符就永久找不回来了 ——
行数少数一行、之后每个采样偏移都错一行。回归用例
`utf16_odd_size_file_then_growth_keeps_every_line` 钉住了它（未修复时 2 行被数成 1 行）。

半截换行（写入进程正写到一半，只剩 `0A`）同样不算换行：残片按字节留在 `pending` 里，
等下一批到齐再拼。这条对 GBK 的跨批次多字节字符也一样（`gbk_multibyte_split_across_polls_is_reassembled`
用例钉住了它）。

### 3. 探测永不失败

`encoding::detect_file` 的判定顺序即可信度顺序：

| 依据（`source`） | 条件 | 状态栏说明 |
|------------------|------|-----------|
| `bom` | 文件以 UTF-8 / UTF-16LE / UTF-16BE 的 BOM 开头 | 「由文件开头的 BOM 判定」 |
| `utf8` | 头部 64 KiB 采样是**合法 UTF-8 前缀** | 「自动检测：内容是合法的 UTF-8」 |
| `fallback` | 以上都不成立 | 「自动检测未能判定，按 GB18030 解码（可在右侧改）」 |
| `manual` | 用户在弹窗里指定 | 「手动指定」 |

两个细节：

- **「合法 UTF-8 前缀」而不是「合法 UTF-8」**：采样边界可能正好把一个汉字切成两半，
  用 `Utf8Error::error_len().is_none()` 把「只是没读全」和「真的有非法字节」分开。
  否则一个正常的 UTF-8 中文文件会因为在第 64 KiB 处恰好切在字符中间而被判成 GBK。
- **兜底为什么是 GB18030**：本项目的日志来自中文 Windows 上编译的游戏，非 UTF-8 的日志
  绝大多数是代码页 936 写出来的，而 GB18030 是 GBK/GB2312 的**严格超集** —— 猜它不会把
  本来是 GBK 的文件解坏。真正的 Big5 / Shift_JIS 会被猜错，但那些编码本来就无法可靠区分
  （没有统计模型就是在瞎猜），交给用户在弹窗里看着预览手动选更诚实。

读不到文件（不存在 / 无权限）时探测也不报错，直接返回兜底编码：真正该报错的地方是随后
那次「打开文件」，不该让探测抢先失败。

## 切换编码时发生了什么

`set_encoding` 命令**整体重建该 tab 的会话**，而不是就地改字段：

```
set_encoding(tab_id, "gbk")
  → AppState::replace_session(tab_id)      新 TabSession（搬走过滤条件）+ 旧会话置 stop
  → start_watching_for_session(...)        按新编码重新探测/解析、重读文件尾部
  → emit("log-lines", { reset: true })     前端整体替换视图
```

为什么整体换：编码决定换行符的**字节形态**，一旦变，行索引的采样偏移、`pending` 残片、
已加载窗口、历史游标全部失效。就地重置要在五六个字段上各写一遍，漏一处就是「行号对但
内容错位」这种极难查的 bug；新建一个 `TabSession` 天然干净。唯一需要搬过去的是**过滤条件**
（`Filter` 因此留了一份原始 `FilterSpec`）—— 用户不该因为换个编码就丢掉正在过滤的关键词。

前端这边不需要为「换编码」写任何专门的刷新逻辑：`reset = true` 的既有语义就是整体替换。

**但要小心「自动刷新」开关**：它会丢弃实时批次（那正是暂停的意思 —— 别动我的视图），
而换编码发出的也是整体替换事件 —— 一起丢掉的话正文会**永远**停在旧编码解出来的内容上，
且不会自愈（那个事件不会再发第二次）。因此 `LinesPayload` 多了一个 `apply_when_paused`，
把三类整体替换区分开：

| 来源 | `apply_when_paused` | 暂停跟随时 |
|------|--------------------|-----------|
| 会话重建（打开文件、`set_encoding` 换编码） | `true` | **照旧应用** |
| 文件轮转 / 截断 | `false` | 丢弃 |
| 过滤条件重扫 | `false` | 丢弃（恢复跟随时由 `toggleAutoRefresh` 统一补齐） |

Markdown 视图没有 tail 会话（它是 `read_text_file` 整读），走的是另一条路：带新编码重读一遍。

### 一个必须堵住的时序洞

换会话时，旧会话的监控线程可能正处在「已经取好一批行、还没 emit」的中间态。如果这批
事件抢在新会话的 `reset` **之后**送达，前端会把它当成「追加」合进新视图 —— 正文里混进
一段用旧编码解出来的乱码。

`TabSession::emit_gate` 把这个洞堵上了：监控线程**持锁 emit**，取代方**持锁置 `stop`**。
于是旧会话的最后一个事件一定落在新会话的 `reset` 之前，前端状态天然自洽。
代价是 `replace_session` 可能要等一次 emit（毫秒级）—— 相比「偶发地往正文里掺一段乱码」，
这个代价可以忽略。`close_tab` 走同一把闸门（关掉之后不该再有任何事件）。

**每个发射点都要过闸门。** `set_filter` 是一条独立的发射路径（它由前端命令直接触发，
不经过监控线程）：它同样可能拿着一个已被替换掉的旧会话去 emit，把旧编码解出来的行
当成新会话的结果贴上去，而且不会自愈。所以它也在发射前持闸门、并检查 `stop`。
`tools/verify-encoding.test.mjs` 有一条断言盯住这件事（`state.rs` 里的 `log-lines`
发射点数量必须不超过持闸门的次数）。

至于死锁：锁序恒为 `sessions → emit_gate`，监控线程只取 `reader / all_lines / filter /
emit_gate`、从不碰 `sessions` 表，因此没有环。而且后台线程 emit 并**不等待主线程**
（tauri-runtime-wry 的 `send_user_message` 在非主线程上退化为非阻塞的
`EventLoopProxy::send_event`），所以「持 sessions 锁等闸门」不会与主线程互锁。

## 编码目录

可选编码清单的唯一事实来源是 Rust 的 `encoding::CATALOG`（前端通过 `list_encodings` 取）。
前端再抄一份就会出现第二处要同步的地方 —— 后端加了编码而前端忘了改，用户就在下拉里看不到它。
`verify-encoding.test.mjs` 有一条断言盯住这件事：TS 侧不许出现任何目录 id 的字面量。

| 分组 | 编码 |
|------|------|
| Unicode | UTF-8、UTF-16 LE、UTF-16 BE |
| 中文 | GB18030（GBK / GB2312 超集）、GBK（ANSI 936）、Big5（ANSI 950） |
| 日文 | Shift_JIS（ANSI 932）、EUC-JP |
| 韩文 | EUC-KR（ANSI 949） |
| 西文 | Windows-1252（含 Latin-1）、Windows-1251、Windows-1250 |

刻意不收的东西：UTF-32（`encoding_rs` 不支持，日志里也见不到）、各类 ISO-8859 冷门变体
（列出来只会把列表撑长）。刻意**没有**单独的 ISO-8859-1 条目：WHATWG 标准里
`iso-8859-1` 只是 Windows-1252 的一个**标签**（`encoding::normalize_id` 会把
`latin1` / `8859-1` / `iso-8859-1` 都归一化到同一项），列成两项会让用户以为它们不同。

id 会被写进 localStorage 存档，所以只认小写字母、数字、`.`、`-`、`_`。
`normalize_id` 另外接受一批别名（`cp936`、`936`、`ansi`、`utf8`、`unicode`…），
老存档里的写法不会因为改过 id 而失效。

## 状态栏

- **左侧是行数**：从工具栏右上角搬来的（同一个 `reportTotal` 上报通道）。它是一条
  「跟文件有关、跟操作无关」的只读信息，属于状态栏；工具栏右上角留给真正要点的按钮。
- **右侧是编码**：显示名 + 别名（`GBK · ANSI 936`），带 BOM 时加 ` BOM` 后缀
  （同一个 UTF-8 有没有 BOM，对「首行为什么看不见标题」这类问题是有意义的线索）。
  悬浮提示里再补一句探测依据。
- **表格视图（`client_cfg` 二进制）不适用**：它不按文本解码。此时编码显示为不可点的灰色
  而不是藏起来 —— 直接隐藏会让状态栏在不同视图之间跳动。
- 状态栏**永远显示**（即使一个 tab 都没打开）。它只有 24px 高，有它在窗口底部收边，
  比「打开文件后才突然多出一条」稳定得多。

## 预览怎么实现

复用现有的 `read_text_file`（带 `encoding` 参数）读文件头部 8 KiB，前端截前 14 行 ——
不新增只服务弹窗的后端命令，也不读整篇文件（`verify-encoding.test.mjs` 有一条断言盯住
「不许冒出一个 `preview_encoding` 命令」）。

预览里两个容易误判的地方：

- **结尾一个 U+FFFD**：8 KiB 上限可能正好切在多字节字符中间。`read_text_file` 返回的
  `truncated` 一并带过来，只有确知被截断时才裁掉末行结尾的替换字符；短文件里真实的
  替换字符是判断编码对错的依据，不能被悄悄抹掉。
- **「该编码下有不少字节无法解码」提示**：要同时满足「至少 4 个替换字符」和「占比 ≥ 5%」
  才提示。只要一个就会误报 —— 截断恰好切在字符中间时必然产生一个。

## 持久化

会话存档（`lv-tabs`）的 `encodings` 字段按 tab 顺序记录**用户的选择**：

- 手动指定的编码会存下来，重启后照它打开；
- `auto` 存 `null`（不固化探测结果）—— 文件可能已被别的工具改写成了另一种编码，
  下次打开应该重新探测；
- 老存档没有这个字段，读出来就是 `null`（等价于 `auto`），不需要迁移。

## 测试

```powershell
cd src-tauri && cargo test --lib                  # 后端（含编码探测/切分/索引/UTF-16 端到端）
node --test tools/verify-encoding.test.mjs        # 前端规则 + 前后端契约 + 解码唯一入口守卫
```

后端测试里值得一读的几条：

| 用例 | 钉住的行为 |
|------|-----------|
| `utf16_terminator_matching_is_aligned` | 假换行必须被对齐判定否决 |
| `partial_utf16_terminator_at_tail_is_not_a_terminator` | 半截换行不算换行 |
| `utf16_scan_step_with_an_odd_budget_still_counts_every_line` | 奇数块会让行数少数一行（实测 200 → 133），块长必须对齐 |
| `utf16_odd_size_file_then_growth_keeps_every_line` | 大小是奇数的文件（写了一半）增长后不许丢换行符 |
| `utf16_file_under_lf_term_counts_wrong` | 索引的 `term` 必须与读取路径一致 |
| `auto_detection_does_not_force_utf8_on_invalid_bytes` | 自动探测确实换了编码，没退回 lossy UTF-8 |
| `truncated_multibyte_tail_is_still_utf8` | 采样边界切在字符中间不误判成 GBK |
| `load_history_is_correct_for_utf16` | 2 字节换行下向前翻页到文件头不丢行、行号不漂 |
| `gbk_multibyte_split_across_polls_is_reassembled` | 跨批次残片按字节拼接，不提前解码 |
| `replace_session_stops_the_old_one_and_keeps_the_filter` | 换会话必须停旧线程、搬过滤条件 |

## 已知边界

- **UTF-16 的探测只认 BOM**。没有 BOM 的 UTF-16 无法与「含大量 NUL 的其它编码」可靠区分，
  不做启发式猜测 —— 在弹窗里手动选即可。
- **预览只读文件头部 8 KiB**。头部是纯 ASCII 而正文才有中文的文件（罕见）在预览里看似正常，
  实际可能选错编码；此时正文区会立刻反映真相。
- **不改写文件**。本功能只影响「怎么读」，不提供转码另存。带 BOM 的文件在保存侧不受影响
  （LogLens 本身从不写日志文件）。
- **表格视图（`client_cfg`）不参与**。那是 MemoryPack 二进制解析，与文本编码无关。
